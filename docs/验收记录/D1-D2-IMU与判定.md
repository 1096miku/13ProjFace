## 2. 计划外的实测发现之一：`STATUSINT.Avail` 是窄脉冲（已修）

原计划写法是"查一次 `STATUSINT` 的 Avail 位，没有就返回 `kNotReady`"。真机快速轮询实测（`build/serial4.log`）：

- 轮询 4045 次/秒，其中 `ok=774`（**Avail 只占 19% 的时间**）
- 但数据真实刷新 **100 次/秒**（与配置的 112.1 Hz ODR 相符）

结论：Avail 是每个采样周期里约 **1.94 ms 的窄脉冲**，两个脉冲之间有约 8 ms 间隙（774 ≈ 100 × 7.7 完全吻合）。按 20 ms 周期"查一次就放弃"会丢掉约 80% 的采样机会。

**修法**：`qmi8658a.cc` 的 `ReadSample` 改为**按 1 ms 间隔、覆盖一个完整周期（12 次）的有界重试**（不忙等，避免占满共享 I2C 总线）。修后实测 `ok=10/10 not_ready=0 err=0`，连续 20 秒恒定。

## 4. 计划外的实测发现之二：上电暂态污染静止基线（已修）

真机把标定期前 60 帧的合成量打出来（`build/monitor.log`）：

```
calib |a|*100: 209 209 209 209 209 209 207 176 176 176 176 123 84 84 84 89 98 100 100 100 ...
```

- 头 17 帧 `|a|` 从 **2.09 g** 经 1.76 → 1.23 → 0.84 → 0.89 → 0.98 回落到 1.00 g，持续约 **340 ms**，这是传感器使能后的内部建立过程（同批样本的陀螺始终 ≈0，不是板子在动）。
- 基线取的是上电后头 50 帧（1 s），把暂态算了进去，结果基线合成量只剩 **0.75 g**、方向也歪。

**后果**（实测）：静止时每 3 s 稳定误报一对 `急加速/急转弯`；且 `is_static` 要求三轴偏差都 < 0.06 g，基线一歪就**永远判不出"停车"**。

**修法**：`DrivingMonitor::Feed` 标定分支只累加 `|a|` 落在 1 g ± `calib_mag_band`（默认 0.10 g）内的样本——条件驱动，不硬编码延时，顺带也排除"上电那一秒板子正被拿在手里"。修后基线 `|a|=0.992–0.995 g`，静止时零误报，`kParked` 正常触发（上表 #4/#10）。

新增主机测试 `[标定期滤掉传感器上电暂态]` 覆盖该场景（喂入实测暂态序列后仍须得到 `|a|≈1.000 g` 且静止不误报）。

## 6. 异常与处置

### 6.1 触摸 I2C 故障导致整机 abort（**已缓解：硬件侧，证据待补**）

```
E (194915) lcd_panel.io.i2c: panel_io_i2c_rx_buffer(145): i2c transaction failed
E (194915) FT5x06: esp_lcd_touch_ft5x06_read_data(179): I2C read error!
ESP_ERROR_CHECK failed: esp_err_t 0x103 (ESP_ERR_INVALID_STATE)
  at managed_components/espressif__esp_lvgl_port/src/lvgl9/esp_lvgl_port_touch.c:127
```

- `ESP_ERROR_CHECK(esp_lcd_touch_read_data(...))` 是**上游托管组件里写死的**：触摸 I2C 一失败就 abort，整套设备重启。
- `ESP_ERR_INVALID_STATE` 在 `i2c_master.c:726` 的含义是"事务没走到 `I2C_STATUS_DONE`"，即**从机没应答(NACK)**；不是超时（超时会打 `I2C transaction timeout detected`，日志里没有），也不是抢锁（抢不到锁返回的是 `ESP_ERR_TIMEOUT`，见 `i2c_master.c:1008`）。
- 因此**与本次任务 4/5 的代码无关**：触摸读取走 LVGL 任务、访问的是另一个器件（FT6336 @0x38）；且 I2C 驱动有互斥锁。
- 触发时机与整机负载相关：多在 WiFi 连接 + 唤醒词模型加载 + 音频输入使能之后；一旦 abort，从机被留在卡死状态，之后每次启动失败得更早（从 8.6 s 提前到触摸初始化 460 ms），只有断电才能恢复——与本次会话中多次出现的"总线卡死"同族。
- 待办：换更粗的 USB 线/主机直连 USB 口/独立 5V 供电后复测；若仍复现，需查 FT6336 供电与 FPC 接触。**不建议**改 `managed_components`（重新解析依赖会被覆盖，且治标不治本）。
- **后续（2026-09-17 用户反馈）**：按上述硬件方向处理后**已能长时间稳定运行、未再复现 abort**。具体动作（换线 / 直连 / 独立供电中的哪几项）与连续运行时长**尚未记录，证据待补**——补齐之前只算**暂时缓解**。代码侧根因未消除（上游 `esp_lvgl_port_touch.c:127` 的 `ESP_ERROR_CHECK` 仍在），触摸再次 NACK 仍会 abort 整机。权威条目见 `docs/BUGS.md` 的 **BUG-006**。

### 6.2 物理连接的脆弱性（已知）
- 大幅度动作会让板子重启，复位原因全是 `rst:0x15 (USB_UART_CHIP_RESET)`（主机侧 RTS 被拉动），不是崩溃也不是掉电；把 USB 线做应力释放后复测，本轮 195 s 内零重启。

### 6.3 计划自带的两个 bug（已修）
1. **`%lld` 必崩**：计划任务 5 的 `LogEvent` 用 `%lld` 打印 `int64_t`，而本工程是 `CONFIG_NEWLIB_NANO_FORMAT=y`，nano 版 `vfprintf` **不支持 64 位整数格式**，只消费 4 字节导致后续可变参数全部错位，`%s` 读到 `NULL` 并在 printf 内部 `memchr` 上踩空指针（`LoadProhibited`，100% 必现）。改为只使用 32 位整数与浮点格式。
2. **`ulStackDepth` 是字数不是字节**：计划里 `heap_caps_malloc(kTaskStackBytes)` 配 `xTaskCreateStaticPinnedToCore(..., kTaskStackBytes, ...)`，会让任务按 4 倍大小使用 4 KB 缓冲区（S3 上 `sizeof(StackType_t)==4`）→ 立刻踩内存。改为传 `kTaskStackBytes / sizeof(StackType_t)`。

### 6.4 基线标定窗口的固有脆弱性（设计取舍，未改）
基线只在**上电后头 50 帧**标定一次。§4 已让"上电时板子在动/传感器未稳定"不再污染基线，但如果设备安装角度在运行中变化，基线不会自动重标。是否需要"运行中重标定"留待后续计划决定。
