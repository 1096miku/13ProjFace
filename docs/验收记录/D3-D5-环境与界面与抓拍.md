## 5. 局限（如实记录）

1. **环境数据是模拟源**，不是真实传感器（本板 I2C 地址已占满，计划书 §11 已列为已知限制）；界面上的"模拟"标注是刻意保留的。
2. **无 RTC**：事件时间只有"开机以来的毫秒"，页面与 JSON 里都不写"今日"。
3. **抓拍与预览分辨率都是 QVGA 320×240**，抓拍 JPEG 约 6–11 KB。
4. **帧率是 10–15 fps，不是稳定的 16 fps**：瓶颈是 LVGL 把 320×240 RGB565 画布经 SPI 刷到屏（约 30 ms/帧），不是相机或取帧。计划要求的 ≥10 fps 在典型情况下满足，长跑后段会贴到 10.0。
5. **内部 RAM 低水位只剩 1003 B（D4 实测，D5 只处置了一半）**：`free sram` 稳态 17.8~19.4 KB，但小智拍照路径（JPEG 编码 + 上传）瞬时把内部堆压到 **1003 B**（`build/acceptance_d4e.log`）。D5 的处置：① `kWorkerStackBytes` 8192 → **6144**（D5 实测余量仍有 `worker 栈余量 4032~4080 B`）；② HTTP 任务栈**放 PSRAM**、HTTP 路径**完全不读 flash**（`httpd_config_t::task_caps = MALLOC_CAP_SPIRAM` + `SnapshotStore` 的 PSRAM 缓存）——新功能对内部 RAM 的常驻占用因此只有 **3.4 KB**（httpd 控制块与 socket），而不是计划里"6 KB 内部栈"那一档。**仍然不要**把会碰 flash 的任务栈放到 PSRAM（BUG-024，其「补充（D5）」写明**读**路径同样成立）。**但这不等于问题解决了**：D5 实测"实时画面页在跑 + HTTP 每 5 s 一轮 + 语音"就把 `minimal sram` 一路打到 **5703 → 1287 → 395 B**（比 D4 的 1003 B 还低，§8.4），并在同一窗口让小智拍照上传失败（BUG-028）。**不过这是负载相关的、不是稳态缺陷**：用户安静长跑 73.8 分钟那一段里 `minimal sram` 是 **9115 B**、`free sram` 17.9~18.4 KB——也就是说日常使用下内部 RAM 是健康的，只有把压测/预览/拍照同时压上去才会贴到 1 KB。**结论：Plan C 要再加常驻内部 RAM 的模块（MQTT、离线命令词）之前，必须先按同一套口径量一次并留出余量。**
6. **BUG-006（触摸 I2C 一次 NACK → 整机 abort）未修**：D3 在 **332.65 s** 复现，D5 带负载测试又在 **145.92 s** 复现（签名逐字一致，见 §8.4 与 BUGS.md）。它让"连续 2 小时不重启"这类指标**很难在加压条件下达成**（用户 2026-09-17 决定暂不修，2026-09-18 再次确认不必重提修复方案）。**注意别只数复位总数**：§8.4 那份 40 分钟日志里 18 次复位只有 8 次是本条，另外 5 次真掉电、5 次是烧录与抓取脚本重连造成的；安静环境下同一版固件至少连续 1181 s 无复位。
7. **相机与预览的共存仍然脆弱**：本轮已把两个明确根因修掉（BUG-024/025），但 `EV-VSYNC-OVF` 仍偶发（588 s 里 2 次，能自恢复），`PSRAM DMA mode disabled` 下驱动每帧要软件搬 153,600 B 这个负载源没有消除。
8. **小智拍照的上传会间歇性挂死**（`fb_count=3`+`LATEST` 那一版第一次出现：`JPEG encoding time` 都没打出来 + `Wait for HTTP headers receive timeout` 两次）。D5 让它从"出现过一次"变成"**间歇性可复现**"：拍到 + 编码（46~53 ms）都正常，上传却可能拿不到响应——有时 950 ms 就成功、有时挂 30~55 s 后超时。**四轮 A/B 已排除 D5 的责任**（HTTP 服务整个关掉照样卡，同一版固件里也成功过），也排除了端点侧（PC 直连 46 ms 正常）。**根因未定**，四个候选解释与后续该抓什么见 **BUGS.md BUG-028**；Plan C 动"抓拍上传"这条演示链路之前先读那一条。

## 6. 环境与操作要点（本轮踩到的）

1. **串口号会跟着 USB 重新枚举跑**：本轮同一块板依次出现在 `COM13 → COM12 → COM13 → COM10/COM13 → (全部消失) → COM10+COM13`。抓取脚本**必须遍历候选端口**，写死一个必然漏掉开机日志（BUG-018）。两个口都在同一块板上（MAC `e8:3d:c1:fb:a2:60`）。
2. **抓取脚本在 USB 掉线重连时会拉 RTS 把板子复位**：日志里 `rst:0x15 (USB_UART_CHIP_RESET)` + `### port error ... I/O operation has been aborted` 成对出现，**不是固件崩溃**，别误判。
3. `idf.py` 在本会话的沙箱下必须放宽权限（`danger-full-access`），否则 `PermissionError: [WinError 5]`（BUG-008）。
4. 烧录：改分区表后跑过一次 `idf.py flash`（会写 `0x8000`）；之后只改 app 时用 `idf.py -p <PORT> app-flash` 更快。
5. **构建要确认日志里真有新编译的 `.obj` 行**：`reconfigure` 失败时 `&&` 会让 `build` 根本不执行，而 `last_build.log` 留着上一轮的旧内容。
6. 复位优先"拔插 USB"，不要按 RST（BUG-005：复位落在 I2C 事务中间会把总线钳死）。

### 10.4 BUG-033：补上"长按 BOOT 进配网"

| 项 | 结论 |
|---|---|
| 现象 | 用户换网络时**进不去配网**；"按 BOOT 会重启" |
| 根因 | 本板只有"启动阶段单击 BOOT"一条路；而 GPIO0 是启动 strap，**上电时按住 = 进 ROM 下载模式**（固件不跑），那条路实际踩不准 |
| 修法 | `boot_button_.OnLongPress(...)` → `EnterWifiConfigMode()`（其它 7 块板的既有惯例） |
| 验证口径 | 长按 2 s → 串口 `长按 BOOT → 进入配网模式` + `EnterWifiConfigMode called` + `Starting config AP`，屏幕给出热点名与网址；**不重启芯片** |

### 10.5 BUG-035：进配网必定重启（80 端口冲突）—— 用户"按 BOOT 会重启"的真根因

补上长按之后配网**能进了**（`Access Point started with SSID Xiaozhi-A261`），但立刻重启，串口给出决定性的两行：

```
E (13870) httpd: httpd_server_init: error in listen (112)     ← 112 = EADDRINUSE
ESP_ERROR_CHECK failed ... wifi_configuration_ap.cc:232 (httpd_start)
```

配网 AP 的网页服务器用 `HTTPD_DEFAULT_CONFIG()`，而我们 D5 的局域网服务也占着同一组端口——**冲突有两处**：
先是数据端口 80（`error in listen (112)`），把我们的服务挪到 8080 之后，**控制端口 32768**（`esp_http_server.h` 的 `ESP_HTTPD_DEF_CTRL_PORT`，两边都是默认值）又炸出
`error in creating ctrl socket (112)`；两处都是 `EADDRINUSE` + 上游 `ESP_ERROR_CHECK(httpd_start(...))` 不检查返回值 → abort。
**修法**：局域网服务两个端口都错开（`kHttpPort = 8080` + `ctrl_port = 32769`）；配网 AP 保留 `192.168.4.1:80`。
另有一条"看运气"的表象：我们的服务在 `StartNetwork()` 里先起，**配网后进必挂、在它起来之前进配网反而是好的**，所以现场时好时坏。
D5 的 §8.1 表里"端口 80"是当轮原始记录，已在表头注明变更。

**复测（`build/acceptance_config_mode3.log`）**：长按 BOOT → `长按 BOOT → 进入配网模式` → `StateMachine: idle -> wifi_configuring` → `Starting config AP` → `Access Point started with SSID Xiaozhi-A261`，
**两条 `httpd_server_init` 报错都不再出现**，配网网页可用（日志里能看到 AP 侧的 SSID 扫描列表）。✅ 本轮修复有效。
⚠️ 该 boot 在进入配网 35 s 后被 **BUG-006**（触摸 I2C NACK → `esp_lvgl_port_touch.c:127` abort）打断——与配网无关，是既有的、已决定不修的那条。
